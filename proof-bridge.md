# Proof-Bridge: Lean & SMT

Die `ProofBridge`-Schnittstelle (`app/src/main/java/de/regelsuche/proof/`) verbindet den Regel-Lifecycle (`CandidateProofStatus`) mit reproduzierbaren Beweisartefakten und optionalen externen Prover-Läufen.

## Ablauf

1. `ProofBridge.prove(left, right, assumptions)` erzeugt ein Skript in der Zielsprache und liefert `ProofAttempt(status, artifact, tool)` zurück.
2. `ProofBridgeService.attemptWithDetails(candidate, assumptions)` schreibt das Artefakt optional nach `.lean`, `.smt2` oder `.txt`.
3. Ohne `ProverExecutor` bleibt das Ergebnis auf dem von der Bridge gelieferten Status, normalerweise `FORMALLY_PROVABLE`.
4. Mit konfiguriertem `ProverExecutor` startet der Service Lean, Z3 oder cvc5 als externen Prozess mit hartem Timeout und erfasst Exit-Code, `stdout` und `stderr`.
5. Nur `PROVER_CONFIRMED` hebt den Kandidaten auf `FORMALLY_PROVED`. Fehlende Werkzeuge, Timeouts, Prover-Fehler oder lediglich erzeugte Skripte tun das nicht. Ein bereits höherer Kandidatenstatus wird nie abgesenkt.

Die persistente Job-Orchestrierung über `ProofJobScheduler`, `CompositeProofWorker`, `LeanProofWorker` und `SmtProofWorker` ist in [`proof-workbench.md`](proof-workbench.md) beschrieben.

## Bestehende Bridges und Worker

### `LeanProofBridge` / `LeanProofWorker`

`LeanProofBridge` erzeugt bewusst zunächst ein Lean-4-Theorem-Skelett:

```lean
-- Auto-generated by Regelsuche LeanProofBridge
-- left  : a / b * b
-- right : a
-- assume NON_ZERO(b != 0)
theorem regelsuche_lemma (h0 : b ≠ 0) : a / b * b = a := by
  sorry
```

Die Bridge allein führt Lean nicht aus und liefert `FORMALLY_PROVABLE`. `LeanProofWorker(Path)` konfiguriert zusätzlich `ProverExecutor.lean()`. Der Executor akzeptiert einen Lauf nur bei Exit-Code 0 und wenn die Prover-Ausgabe kein `sorry` meldet; das unveränderte Skeleton kann daher nicht fälschlich als bewiesen gelten. Für `FORMALLY_PROVED` muss das Artefakt einen tatsächlichen, von Lean bestätigten Beweis enthalten.

### `SmtProofBridge` / `SmtProofWorker`

`SmtProofBridge` erzeugt ein SMT-LIB-2-Skript, beispielsweise für QF_NRA:

```smt
(set-logic QF_NRA)
(declare-const a Real)
(declare-const b Real)
(assert (distinct b 0))
(assert (not (= (/ (* a b) b) a)))
(check-sat)
(exit)
```

Die Bridge allein liefert das Skript und `FORMALLY_PROVABLE`. `SmtProofWorker(Path)` verwendet standardmäßig `ProverExecutor.z3()`; alternativ kann ein anderer Executor wie `ProverExecutor.cvc5()` injiziert werden. Nur ein erfolgreicher Prozess mit Solver-Ausgabe `unsat` ergibt `PROVER_CONFIRMED` und damit `FORMALLY_PROVED`.

## Eigene Bridge oder Prover-Anbindung

Eine eigene Zielsprache implementiert `ProofBridge` und liefert einen passenden `ProofAttempt`. Konvention für das `tool`-Feld:

* `"lean4"` → Dateiendung `.lean`
* `"smtlib2"` → Dateiendung `.smt2`
* sonst → Dateiendung `.txt`

Für die tatsächliche Ausführung kann ein `ProverExecutor` mit Befehlszeile, Suffix, Timeout und einem expliziten `SuccessPredicate` konstruiert werden. Die Befehlszeile ist eine vertrauenswürdige Entwicklerkonfiguration; sie darf nicht aus ungeprüfter Benutzereingabe aufgebaut werden.

## Zusammenspiel mit Assumptions

Beide Bridges nehmen die `List<Assumption>` der Kandidatenregel entgegen. Sie übersetzen die kanonischen Kinds (`NON_ZERO`, `POSITIVE`, `NON_NEGATIVE`, `DOMAIN_MEMBERSHIP`, `CUSTOM_PREDICATE` und weitere Domain-Kinds) in die Zielsprache. Eigene Assumptions sollten ihre `symbols()`-Liste setzen, damit die Bridges Referenzen korrekt erzeugen können.
