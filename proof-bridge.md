# Proof-Bridge: checked Lean and lossless SMT

The application `ProofBridge` API now delegates to the same typed
`SolverIr.Obligation` and portfolio backends as other proof consumers. It does
not maintain a second expression grammar or replace unsupported assumptions
with `True`. Domain-specific campaigns belong in their consuming projects;
this repository supplies reusable proof infrastructure and generic controls.

## Generation is not confirmation

`LeanProofBridge.prove(...)` and `SmtProofBridge.prove(...)` only generate an
artifact. Their `FORMALLY_PROVABLE` value means that a supported script was
prepared, not that its proof tactics succeeded. Unsupported translation returns
a non-confirming result. Both bridges also accept an existing typed obligation,
including inequalities. Legacy string and assumption inputs are translated once
by `ProofObligationAdapter`; opaque or inconsistent assumption syntax is rejected.

`ProofBridgeService.attemptWithDetails` binds execution to the newly reconstructed
request, including goal, declarations and all current premises. It rejects a
valid artifact for a different request before invoking a tool. An incoming
candidate's unbound `FORMALLY_PROVED` flag or a bridge-produced success label is
not fresh evidence and cannot preserve or authorize that status.

## Lean: actual proofs, exact theorem type and transitive axioms

`LeanSourceRenderer` emits a closed real theorem and a bounded tactic program,
not a `sorry` skeleton. Arithmetic, field simplification, positivity, nonlinear
arithmetic and selected mathlib lemmas are attempted. Supported analytic calls
use `Real.exp`, `Real.log`, `Real.sqrt`, `abs` and `Real.rpow`, never arbitrary
uninterpreted functions. Natural powers have their natural-number exponent
semantics, including values beyond 64. Real powers require positive bases;
logarithms and square roots require their supported domain premises. Unsupported
sorts, relations, domains, calls and resource bounds are rejected explicitly.

The generated wrapper checks

```lean
theorem regelsuche_bound : expectedClosedType := @regelsuche_lemma
```

and computes the transitive axiom dependencies using `Lean.collectAxioms`.
Only `propext`, `Classical.choice` and `Quot.sound` are admitted by this policy.
Direct or indirect additional axioms, hidden `sorryAx`, a different conclusion
or an extra premise cannot satisfy this wrapper. The actual checked `.olean`,
source, exact native request, translation, result, execution, audit, pinned
configuration and version/diagnostic output are retained in a fresh directory.

A single audit must match the exact request hash and a fresh invocation nonce.
The generated input is regenerated byte-for-byte before execution; arbitrary
or edited Lean programs are not accepted. The configured Lean/mathlib project
and executable are trusted code: this is not a sandbox for malicious Lean
extensions. `lean-toolchain` and `lake-manifest.json` are required and bound;
the reference environment is `.ci/lean-proof`.

A failed bounded proof attempt is `UNKNOWN`, not a mathematical refutation.
Timeout, truncated output, missing tools or an invalid audit cannot authorize a
certificate. Successful proofs are conditional on exactly their declared
premises. Their satisfiability is **not** established by proving the implication.
The closed theorem currently concerns the supported real-expression fragment,
not arbitrary quantified sets, infinite sums or limit theorems.

### Independent rebuild of retained Lean source

`LeanEvidenceRebuilder.rebuild` takes the exact expected `SolverIr.Obligation`,
the trusted original `SolverExecution.result().certificateHash()`, and the
retained attempt directory. The original certificate binds the project
location by hash and both pin files separately. The rebuilder checks the
retained artifact hashes, reconstructs the exact source using the audit nonce,
and compiles it in a fresh output directory with a separate prepared Lean
project. Both pin files and the observed tool version must match. The fresh
kernel audit must bind the same theorem and report the same transitive axiom
set. The rebuilt `.olean` is hashed separately.

`rebuild.txt` binds the original and rebuilt certificate hashes. A rebuild
receipt does not participate in proof admission or cache status. The caller
must prepare and trust the second Lean/mathlib installation. Distinct project
locations and matching pins do not attest the installed binaries or package
files. Previously retained certificates lack the three environment fields and
need a fresh original execution before they can be rebuilt.

## SMT: no opaque analytic fallback

`SmtProofBridge` uses `SmtProofArtifacts` and the existing lossless
`SmtLibRenderer`. Goals and all structured assumptions are included. Algebraic
real arithmetic and supported fixed natural powers retain their actual
semantics. Division requires an encoded nonzero or strict-sign premise.
Analytic calls and unsupported symbolic powers are rejected, not encoded as
uninterpreted functions. Use the Lean route for supported real-function proofs;
there is no automatic meaning-changing fallback.

`ProverExecutor.z3()` calls the existing Z3 backend with the exact typed request.
A reported `unsat` alone is insufficient: a second invocation must retrieve a
nonempty proof object. `executeWithEvidence` retains the complete SMT inputs,
stdout/stderr, invocation status and proof object as well as the canonical
native evidence chain. The stored proof text has exactly the certificate hash
reported by the backend.

### Optional independent polynomial proof replay

`RetainedAttempt.replaysEqualityProof(expected)` additionally binds the expected
obligation, the original confirmed execution and the retained proof hash before
calling the Java checker. `Z3EqualityProofReplay.verifies(expected, object)`
checks the same mathematical derivation using only the typed statement and
object text. Neither entry point invokes an external solver. They return a
Boolean result separately from the existing solver status and capabilities:
`SMT_UNSAT_PROOF_OBJECT` still describes the external proof object, not an
independently replayed proof. An unsupported or exhausted replay returns
`false`; it does not refute the theorem or revoke the external execution.

Real terms reuse `SolverIr.Expression`: declared real symbols, exact decimal
literals, addition, subtraction, multiplication and positive integer powers
with exponents 1–20. Exponent zero is rejected: native Z3 `^` does not establish
the convention `0^0 = 1`, so replay cannot import that normalization from the
polynomial backend.
The native syntax can contain n-ary arithmetic arguments, unary minus and
`to_real` on integer literals. A quotient of literal constants is accepted
only when exact decimal division terminates: `(/ 1.0 2.0)` denotes exactly
`0.5`, while `(/ 1.0 3.0)`, division by zero and symbolic denominators remain
unsupported. No rounded coefficient enters replay. Native argument positions
remain available to the congruence checker even when an n-ary term is folded
into the existing binary IR.

The supported proof rules are `asserted`, `refl`, `symm`, ordered `trans`/`trans*`,
`monotonicity`, `rewrite`, `mp` and two-complement `unit-resolution`.
Congruence checks the operator, argument count and an exact equality proof for
each changed argument. A proof carrying premise dependencies must cover at
least one changed argument position that has not already been covered; an
unchanged or already covered position alone cannot justify those dependencies.
Dependency-free reflexivity, including exact numeral coercions, is permitted.
This is a local relevance check, not a proof that the overall premise set is
minimal. Boolean equality, negation and constants support the
equivalences used by native normalization proofs; `mp` checks both sides of
the claimed equivalence. Every polynomial `rewrite` is checked without
premises by `PolynomialNormalFormSolverBackend`. The native rule name grants
no authority. A failed polynomial identity check is never interpreted as a
disequality valid for every assignment: `x = 0` is neither constantly true
nor constantly false.

Assertions must match the original premises or exact negated goal after exact
numeral/coercion normalization. An algebraically equivalent replacement is not
an authorized asserted leaf. Acceptance requires a derivation of `false` using
the exact negated goal and every distinct supplied premise. Duplicate and
unused premises are rejected. Term (`?x`), formula (`$x`) and proof (`@x`)
bindings have separate checked kinds. Multi-binding `let` expressions are
parallel; duplicate, shadowed and forward bindings are rejected.

The admission limits are conservative resource limits, not a measured speed
advantage or a complete cost model:

| Admission check | Limit |
| --- | --- |
| Proof object | 131,072 UTF-8 bytes; also at most 131,072 Java characters |
| Wire syntax | 8,192 nodes, depth 128, atom length 256 |
| Typed request | 128 real declarations and 128 equality premises |
| Native arithmetic arguments and scalar literal text | 128 arguments; 256 characters per literal |
| Expanded term/formula size | 4,096 per value; cumulative admission charge 65,536 |
| Polynomial expansion estimate | 256 monomials, total degree 32, literal power exponent 1–20 |
| Coefficient admission estimates | At most 4,096 bits each for coefficient numerators and a common denominator |
| Uncached polynomial leaf checks | 128 calls; cumulative size-times-monomial estimate 262,144 |

Coefficient growth is bounded before normalization, including constant
coefficients embedded in nonconstant terms. The estimates can reject an
expression whose fully reduced coefficients would be smaller; they do not
promise a minimal or exact operation count. Limits are checked before the
corresponding polynomial leaf is dispatched.
Inequality theory lemmas (`th-lemma`), quantifiers, general clause resolution,
scoped hypothesis/lemma discharge and analytic calls are outside this replay
grammar. General binders, sets, summability and limit semantics, broader replay
grammars, learned tactics and imported-lemma dependency evidence in #1066
remain separate work. Issue #1066 remains open.

### Native evidence and reproduction

The [four retained Z3 4.8.12 fixtures](../regelsuche-solver-portfolio/src/test/resources/z3-proof-replay/README.md)
cover distributivity, addition of zero, exact decimal coefficient collection
and a rejected conditional object. The conditional request `x = y ⊢ x*z = y*z`
returns `unsat` externally, but the captured default object omits the `x = y`
asserted leaf and uses a condition-dependent `rewrite`. Independent replay
rejects it both with the original premise and with the premise removed.
This is a coverage boundary of the retained object and checker, not a claim
that the conditional mathematical statement is false.

The checked-proof suite also obtains fresh objects through
`executeWithEvidence` for distributivity, decimal collection, cubic expansion,
the earlier symbol-equality chain and its symmetry control. Exact statement
binding is tested with changed coefficients, reversed goals and added
premises; retained-file controls exchange genuine proofs and truncate an
object. The focused replay tests check explicit congruence derivations and
forged rewrites independently of a Z3 installation. Native proof choices may
differ between Z3 versions; a different rule grammar is not automatically
accepted. See the commands below to run the real-tool lane without treating
skipped tests as evidence. These controls establish bounded replay behavior,
not general SMT proof completeness or a solver performance comparison.

## Process success is not mathematical evidence

The public `ProverExecutor(command, ...)` constructors are transport-only.
A custom command such as `true` or `cat`, even with a permissive success
predicate, can return only `PROCESS_SUCCEEDED`, never `PROVER_CONFIRMED`.
The raw `cvc5()` factory also remains transport-only until a checked artifact
adapter is supplied. Previous exit-code-only promotion is intentionally removed.

Only the checked `lean(...)` and `z3(...)` factory paths can confirm the exact
request. The worker, demo and web tests explicitly prevent transport success
from being displayed as a mathematical proof. Custom worker injection itself
remains trusted application configuration, not user-supplied proof authority.

## Configuration and reproduction

For Lean configure `REGELSUCHE_LEAN_PROJECT` or `regelsuche.lean.project` to a
pinned, prepared Lean/mathlib project. An installed bare Lean executable is not
enough. `regelsuche.proof.evidence` controls the default evidence root; the
explicit `ProverExecutor.lean(project, evidenceRoot)` and `z3(evidenceRoot)`
factories support application-owned directories.

Generic contract tests do not need a prover installation. Real tool tests are
separate and must actually execute, not merely be skipped:

```sh
z3 --version
mvn -B -pl regelsuche-solver-portfolio -am \
  -Dtest=Z3EqualityProofReplayTest,Z3SmtSolverBackendTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

This targeted replay run requires Z3 on `PATH`; check that the native-object
tests execute without skips. The independent Java fixture checks also run
when Z3 is absent, but alone do not establish the fresh-execution result.

For the separate Lean and application-bridge real-tool controls:

```sh
export REGELSUCHE_REAL_LEAN=true
export REGELSUCHE_LEAN_PROJECT="$PWD/.ci/lean-proof"
(cd .ci/lean-proof && lake update && lake exe cache get)
mvn -B -pl app -am \
  -Dtest=CheckedLeanRealTest,CheckedProofBridgeRealTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

This run also requires Z3 on PATH. The required `checked-proofs` job in the
existing CI workflow installs the reference tools and retains their evidence.
It supplements the unchanged complete Gradle, Maven, benchmark and Docker
authorities rather than replacing them. Compiler warnings, skipped real-tool
tests outside that job, and unrelated failures are not successful validation.

The separate-project rebuild test in `CheckedLeanRealTest` also needs
`REGELSUCHE_LEAN_REBUILD_PROJECT` set to a second provisioned project with
byte-identical `lean-toolchain` and `lake-manifest.json` pins. The checked-proof
job provisions both projects through Lake and uses its shared build-artifact
cache. Each project has its own package checkout and build directory.

See [Proof Workbench](proof-workbench.md), [Solver IR](solver-neutral-ir.md) and
[Solver portfolio](solver-portfolio.md) for the existing orchestration contracts.

## Persistent cache admission

Worker display IDs are not cache scopes. The current `proof-cache/v2` identity
binds the evidence contract and backend configuration. Lean includes the pinned
toolchain and manifest; Z3 includes detected version and command configuration.
Composite workers recompute the scopes of their members. A configuration change
during an attempt prevents publication of that attempt's status.

The persistent cache currently stores statuses, not independently replayable
proofs. Therefore `FORMALLY_PROVED` is never admitted from a cache hit, even for
a current identity. A fresh backend execution is required. Non-proof generation
results remain reusable in the same scope. Old entries are not deleted or
silently upgraded; legacy identities cannot authorize the new evidence contract.

### Scoped solver obligations (v2)

Construct scoped statements through the same Java `SolverIr.Obligation.create` boundary.
Including `Theory.SCOPED_ANALYSIS` selects the [v2 schema](schemas/regelsuche-solver-obligation-v2.schema.json).
A `Predicate.holds(id, proposition)` introduces a named assumption. A
`Goal.holds(proposition)` requests a proof of the proposition. Arithmetic
goals and assumptions can also be used. Declarations refer to free symbols by
name. `Bound(0)` refers to the immediately enclosing binder and `Bound(1)` to
its parent. Construction rejects out-of-scope indices. Alpha-equivalent
binders use the same wire representation.

| IR construct | Checked interpretation |
| --- | --- |
| `Binder(FORALL/EXISTS, sort, p)` | Universal or existential quantification over the supported sort |
| `Binder(SET_OF, REAL, p)` | Set of reals satisfying the predicate |
| `Binder(SEQUENCE, NATURAL, t)`, `Binder(FUNCTION, REAL, t)` | Natural-indexed real sequence or real-valued real function |
| `eq`, `ne`, `le`, `lt`, `and`, `or`, `not`, `implies` | Typed comparison and propositional operations |
| `mem`, `subset`, `union`, `inter` | Real set membership, inclusion, union, intersection |
| `nat`, `of_nat`, `succ`, `at` | Natural numeral, real coercion, successor, function application |
| `summable(f)`, `has_sum(f,a)`, `tsum(f)` | Mathlib `Summable`, `HasSum`, and totalized `tsum` |
| `tends_to(f,a)`, `limit_at(f,x,a)` | Natural sequence limit at infinity, or function limit along the full neighborhood filter at x |

The function limit uses `nhds x`, which includes the value at x. Statements about
punctured neighborhoods need a separate operator. A `tsum` term alone does not
assert convergence. The caller can state summability or an exact sum separately.
The lossless translator checks application arities, sorts, binder domains and
the existing real-domain conditions before execution. A bounded tactic failure
yields `UNKNOWN`. Enumerating a witness through unification and applying
pinned `HasSum.summable` and `Summable.add` produce ordinary Lean proof terms.
Register the configured Lean backend via `StandardPortfolioBackends.lean`.
Other standard profiles reject v2 requests before execution.

V2 evidence records each imported declaration's name and defining module at
the boundary of the actual proof and its local helper declarations. The
existing axiom traversal follows dependencies through imported declarations.
The recorded module names resolve in the pinned mathlib/Lean environment.
The separate-project rebuild checks the same imported declarations and adds
a second theorem built directly from the IR by an independent translator
using different names, closure order of construction and constructor syntax.
It kernel-checks that the original proof inhabits that statement. The v2
receipt binds the second theorem text. Both translators and the provisioned
Lean installation remain inside the trust boundary. V1 obligations retain
their original wire format, source and rebuild behavior.

#### Transfer of checked lemma applications

`LeanLemmaPlan.learn(training, trustedCertificateHash, retainedDirectory)`
verifies the certificate hash, the exact training obligation and the hash of
its dependency audit. Before receiving the target it freezes up to 32 sorted,
representable mathlib declaration names observed at the imported boundary.
`LeanSolverBackend.using(plan)` tries one application per candidate, with
target assumptions as its only subgoal solver. There is no fallback to the
ordinary search tactics in this trial. Some imported constants originate in
types and will be inapplicable. A successful trial must compile a fresh
kernel-checked theorem and its audit must contain a proposed declaration.
The target certificate binds the frozen plan hash through the generated source,
and the separate-project rebuild reconstructs the same trial. The real
positive control trains on summability of the sum of two summable sequences
and targets a doubled sequence with one premise. Removing that premise is the
negative control. This public transfer control makes no speed or blinded
generalization claim.

#### Quantified witness and induction plans

`ExistentialIntroduction.Statement.toScopedObligation()` exports an existing
witness goal, all its outer parameters and its structured premises for a fresh
formal check. The existing polynomial or assumption leaf remains available for
independent replay. The scoped export of an alpha-renamed witness is identical.

`NaturalInduction.discover(context)` enumerates at most 128 declared natural
predicates from the context. For a predicate `P : Nat → Prop` it matches
two distinct premise leaves, `P 0` and `∀ n, P n → P (n+1)`. The endpoint
of the context is never read during formation. Each returned plan carries the
two exact premise IDs and its reconstructed conclusion `∀ n, P n`. The
renderer chooses the matching plan only for that recipient statement. Lean
checks the generated application of `Nat.rec` to its explicit motive and the
two named hypotheses. The independent statement reconstruction and imported
dependency/axiom audit also run here. This inference covers the primitive
natural-number rule with supplied base and step. Synthesizing those premises
or proving arbitrary well-founded recursive calls requires additional rules.

### Bounded logical discovery and exact DAG replay

`ScopedLogicDiscoveryDomain` implements the standard
`DiscoveryDomain<State, ScopedProofDag, Certificate>` interface. Its seed
payload is the canonical JSON of a v2 solver obligation. Formation inspects
the declarations and premises, generates conclusions, and binds each proposed
DAG to a new exact obligation. A comparison with a chosen endpoint can occur
after formation. The domain accepts up to 32 declarations, 32 premises and
65,536 formation units. It runs its original implication chaining for up to
four rounds to preserve the proof and work bound to each previously retained
proposal. Up to four additional rounds use conjunction projection, existential
elimination and chained implications. The formation ledger counts its declared
source inspections and graph work.

The public finite grammar uses lexical local slots and topologically ordered
children. It supports assumption references, implication and universal
introduction, application, specialization, cuts, local definitions and
unfolding, existential introduction and elimination, conjunction introduction
and projection, disjunction elimination,
classical contradiction, equality substitution, natural induction, strong
natural induction, normalization and checked leaf solving. A recursive use of
the strong induction hypothesis takes both the proposed argument and its
strict-decrease proof. The kernel checks the argument, comparison direction,
scope and motive. An explicit hand-constructed DAG and a source-generated DAG
enter the same receiving boundary. The source generator currently constructs
modus ponens, universal specialization, cases, equality substitution,
double-negation elimination, witnesses and the two natural induction forms.
It also projects both sides of conjunctions and derives a conclusion from
`∃ x. P(x)` and `∀ x. P(x) → Q` when the binder sort and antecedent
match exactly and `Q` is independent of the witness. It checks this
independence inside nested binders. The generated elimination continuation
retains both the local witness and its property, then applies the specialized
universal proof. The receiving kernel checks the resulting term against the
exact closed statement.
The graph allows up to 128 distinct nodes, 512 expanded visits and 64 locals.

`new DomainDiscoveryRunner().run(campaignId, domain, seed, budget)` explores
the source proposals. Its finite countermodel service evaluates constant
propositional and natural-predicate interpretations. It records partial
interpretations and only reports a refutation for a genuine assignment
satisfying all premises and falsifying the goal. The evaluator uses two
separately provisioned pinned Lean projects. The first checks the generated
proof term. The second reads the retained canonical DAG, regenerates that
term, reconstructs the expected theorem type independently and audits the
compiled proof. Both receipts must exist before the domain emits a
certificate. `lean.using(dag).executeWithEvidence(dag.obligation())` exposes
the first receiver directly. Scope checks, candidate formation and finite
model searches carry no proof confirmation on their own.
