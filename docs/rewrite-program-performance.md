# Rewrite-program and AST execution performance

## Scope

This page records the measured execution evidence for issue #530. It separates
three questions that must not be conflated:

1. How much overhead does the immutable `RewriteProgram` interpreter add?
2. How much avoidable work exists in AST parsing, matching, hashing and rewrite
   materialization?
3. Does an executor-level improvement survive complete symbolic search with the
   same semantic work?

The authoritative mathematical resource ledger remains primitive and total
mechanical work. Wall-clock time and allocation are environment-qualified
engineering evidence only.

## Reproduction surface

The ordinary benchmark report is generated by:

```bash
./gradlew :app:jmh
./gradlew verifyJmhBenchmark
```

The scoped allocation report is generated by:

```bash
./gradlew runJmhAllocationBenchmark verifyJmhAllocationBenchmark
```

Published outputs:

- [JMH benchmark charts](../public/dev/bench/)
- [Normalized allocation evidence](../public/dev/bench/allocation.json)

The retained reference measurements use Temurin JDK 21, JMH average time,
one fork, two warm-up iterations, three measurement iterations and one second
per iteration. The allocation slice uses the JMH GC profiler and
`·gc.alloc.rate.norm` in bytes per operation.

## Interpreter result

Synthetic `RewriteProgram` dispatch is measurable at sub-microsecond scale, but
it is not the material bottleneck in a real AST rewrite. On the retained
reference tree, one interpreted/programmed AST-source invocation was within
roughly one percent of the direct AST engine, while nested program topology was
still only a small fraction of one real AST operation.

Therefore a topology bytecode compiler or generated-class backend is not
justified by the preregistered threshold. The JVM already compiles the Java
interpreter; generating additional classes would add compilation, caching and
metaspace cost without addressing the dominant work.

## Prepared AST backend

`PreparedAstRewriteTransformationEngine` preserves the public string boundary
and ordered `Transformation` result while removing avoidable internal work:

- AST sizes are computed from existing `Expr` values rather than formatting and
  reparsing;
- subtree hashes are computed lazily after a rewrite actually succeeds;
- exact `PatternRewriteRule` values reuse one binding pass for matching and
  target construction;
- overridden rule subclasses retain the ordinary reference dispatch.

Differential tests require complete ordered transformation equality, including
application keys, assumptions, rule identities, pack and license provenance.

## Measured results

| Workload | Reference | Prepared | Time reduction | Reference allocation | Prepared allocation | Allocation reduction |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| AST rewrite source | 0.231501 ms/op | 0.091046 ms/op | 60.7% | 586,014.945 B/op | 349,313.255 B/op | 40.4% |
| Fixed-work complete search | 31.814383 ms/op | 17.726460 ms/op | 44.3% | 62,494,845.738 B/op | 42,914,806.675 B/op | 31.3% |
| Targeted complete search | 0.816746 ms/op | 0.484627 ms/op | 40.7% | 1,357,743.139 B/op | 801,642.074 B/op | 41.0% |

This corresponds to approximately 2.54× throughput for the isolated AST-source
workload, 1.79× for the fixed-work search and 1.69× for the targeted search.

## Semantic-work parity

The complete-search comparison retains exact `GoalSearchResult` equality.
Auxiliary counters are identical per search:

| Scenario | Explored | Expanded | Generated transformations | Enqueued | Reached target |
| --- | ---: | ---: | ---: | ---: | ---: |
| Fixed work | 128 | 128 | 338 | 322 | 0 |
| Targeted multi-step | 5 | 5 | 14 | 14 | 1 |

The speedup is therefore not caused by exploring fewer states, generating fewer
transformations or accepting a shorter semantic path.

## Position relative to a theoretical maximum

There is no environment-independent percentage of a universal theoretical
maximum for this workload. Even a perfect matcher must still parse the public
input, inspect the declared rule inventory, construct retained results, format
the public expression and preserve deterministic provenance.

The useful engineering interpretation is narrower:

- the prepared backend removes 60.7% of the measured reference AST-source time;
- 39.3% remains in work that is either semantically required or not yet
  isolated as avoidable;
- complete-search savings settle at 40–44%, because scoring, canonicalization,
  deduplication, frontier operations and result construction remain unchanged;
- allocation falls by 31–41%, confirming that the time result is accompanied by
  less memory traffic rather than a timing-only artifact.

Future optimization should profile those remaining layers separately. It must
not infer search-space improvement from an executor microbenchmark alone.

## Production decision

The accepted direction is:

1. retain `AstRewriteTransformationEngine` as the explicit semantic reference;
2. expose a central backend selection whose production default is Prepared;
3. keep an explicit `REFERENCE` mode for differential testing, diagnosis and
   unsupported cases;
4. require byte-identical canonical evidence and work metrics;
5. fall back only at a declared backend boundary, never by silently swallowing
   arbitrary runtime failures;
6. do not implement topology bytecode unless later evidence crosses the frozen
   material-overhead threshold.

## Claim boundary

These results support only a performance claim for the declared JDK, benchmark
revision and workloads. They do not establish mathematical correctness by
wall-clock timing, reduce canonical mechanical work, prove general scalability
or authorize a flagship discovery result.
