# Performance & Coverage Dashboards

Regelsuche renders all quality pages from checkout-local Gradle outputs and
deploys them only after a successful `ciCheck` run on `main`.

| Dashboard | URL | Checkout source |
| --- | --- | --- |
| Coverage report | <https://carstenartur.github.io/Regelsuche/coverage/> | JaCoCo XML/HTML produced by the repository test graph |
| Test report | <https://carstenartur.github.io/Regelsuche/tests/> | Gradle JUnit XML/HTML produced by the repository test graph |
| Performance report | <https://carstenartur.github.io/Regelsuche/dev/bench/> | validated `app/build/reports/jmh/result.json` |

The shields.io endpoint badges consume the generated JSON files under
`public/`. They therefore reflect the last successfully deployed `main` run.

## Complete standard JaCoCo report

The coverage entry page is generated by JaCoCo's standard HTML formatter, not a
custom percentage table. It contains all 23 modules declared in
`config/quality/coverage-policy.json`, including the isolated SymPy measurement.
Instructions, branches, lines, complexity, methods and classes are visible at
aggregate and module level, with package, class and highlighted-source navigation.

Each module retains its actual JaCoCo execution data, filtered class directories
and source directories under `build/reports/jacoco/test/inputs`. The small Java
assembly adapter uses a separate execution-data store per module: tests of an
application must not silently change a dependency module's canonical coverage.
JaCoCo itself owns analysis and all HTML/XML rendering. The renderer runtime is
retained under `build/reports/quality/coverage-report-runtime` in the existing
verification artifact alongside the Java coverage decision. Local Gradle and
cross-authority CI invoke the same decision and write the v1 JSON and Markdown
reports. Convergence uses the retained runtime without repeating tests or
resolving dependencies.

The decision requires one top-level line counter and one branch counter in
each unnamespaced JaCoCo `report`, with explicit nonnegative counts. Invalid
inputs invalidate the canonical gate reports. A completed decision that finds
coverage violations writes a fresh `FAILED` report for diagnosis.

The publisher checks all six counters against every canonical module XML and
checks line/branch counts against the unchanged successful coverage gate. Missing,
duplicate or inconsistent modules abort publication. The badge explicitly reports
**line coverage**, rounded to two decimals from those same covered/missed counts,
not an independent recursive sum of instruction counters. Its green colour means
the existing repository and module coverage gates passed; no floor is lowered.

In split CI, the Gradle producer generates test pages only. After the isolated
SymPy report is joined, convergence renders and validates the complete coverage
site once and retains it in `coverage-verification`, including `jacoco.xml`.
Pages restores that complete site rather than publishing a producer's subset.

Native GitHub coverage upload is not part of this report path or `ciCheck`.
An optional future PR annotation integration must remain a separate publication
using the official upload action, without making the local verification result
or this standard report depend on an external coverage service's availability.

## Local commands

```bash
# Coverage and test pages
./gradlew test jacocoTestReport generateCiPages

# JMH result validation, badge and static report
./gradlew verifyJmhBenchmark

# Complete CI report set
./gradlew ciCheck
```

`verifyJmhBenchmark` runs the JMH suite, validates every
benchmark/parameter identity and finite primary metric, and writes:

```text
app/build/reports/jmh/result.json
public/dev/bench/badge.json
public/dev/bench/index.html
```

To replay the publication decision on retained raw JMH JSON with JDK 25 and Maven, run:

```bash
mvn -pl regelsuche-quality -Dregelsuche.jmh.publicationResult=/absolute/path/to/result.json verify
```

Maven writes `badge.json` and `index.html` under
`regelsuche-quality/target/reports/quality/jmh-publication/`. The Gradle
producer calls the same Java verifier on the live measurements. Both require
the six-warmup policy, exact benchmark inventory and units, and a finite score
and uncertainty. The publication fails when the lower confidence bound exceeds
the versioned baseline score times its material-regression ratio.

The performance page is a deterministic static report. The checkout also owns
the content-bound v3 regression decision and the Java renderer for two retained
JMH history snapshots and 29 SVG charts; see
[performance history](performance-history.md). Neither history nor regression
interpretation is delegated to a GitHub Action.

## Verification and publication boundary

`.github/workflows/gradle.yml` separates expensive authorities within one workflow:

1. Gradle, isolated JMH, isolated SymPy runtime, complete Maven/Docker and the
   external polynomial comparison execute their checkout-owned commands.
2. Required `verification` rejects failed authorities, joins the coverage
   inputs, reruns the unchanged coverage verifier, renders the complete JaCoCo
   site, and collects the complete
   [quality acceptance evidence](quality-acceptance-evidence.md).
3. `publish-pages` downloads the retained outputs, combines `docs/` and `public/`, and
   deploys the static files through GitHub Pages.

The publication job has no test selection, assertions or benchmark interpretation.
It cannot turn a failed verification into a successful deployment. There is no
additional benchmark workflow and no `gh-pages` branch write that creates a
second Pages build run.
