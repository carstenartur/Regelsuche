# Proof-Bridge: checked Lean and lossless SMT

The application `ProofBridge` API now delegates to the same typed
`SolverIr.Obligation` and portfolio backends as other proof consumers. It does
not maintain a second expression grammar or replace unsupported assumptions
with `True`. Domain-specific campaigns belong in their consuming projects;
this repository supplies reusable proof infrastructure and generic controls.

## Generation is not confirmation

`LeanProofBridge.prove(...)` and `SmtProofBridge.prove(...)` only generate an
artifact. Their `FORMALLY_PROVABLE` value means that a supported script was
prepared, not that its proof tactics succeeded. Unsupported translation returns
a non-confirming result. Both bridges also accept an existing typed obligation,
including inequalities. Legacy string and assumption inputs are translated once
by `ProofObligationAdapter`; opaque or inconsistent assumption syntax is rejected.

`ProofBridgeService.attemptWithDetails` binds execution to the newly reconstructed
request, including goal, declarations and all current premises. It rejects a
valid artifact for a different request before invoking a tool. An incoming
candidate's unbound `FORMALLY_PROVED` flag or a bridge-produced success label is
not fresh evidence and cannot preserve or authorize that status.

## Lean: actual proofs, exact theorem type and transitive axioms

`LeanSourceRenderer` emits a closed real theorem and a bounded tactic program,
not a `sorry` skeleton. Arithmetic, field simplification, positivity, nonlinear
arithmetic and selected mathlib lemmas are attempted. Supported analytic calls
use `Real.exp`, `Real.log`, `Real.sqrt`, `abs` and `Real.rpow`, never arbitrary
uninterpreted functions. Natural powers have their natural-number exponent
semantics, including values beyond 64. Real powers require positive bases;
logarithms and square roots require their supported domain premises. Unsupported
sorts, relations, domains, calls and resource bounds are rejected explicitly.

The generated wrapper checks

```lean
theorem regelsuche_bound : expectedClosedType := @regelsuche_lemma
```

and computes the transitive axiom dependencies using `Lean.collectAxioms`.
Only `propext`, `Classical.choice` and `Quot.sound` are admitted by this policy.
Direct or indirect additional axioms, hidden `sorryAx`, a different conclusion
or an extra premise cannot satisfy this wrapper. The actual checked `.olean`,
source, exact native request, translation, result, execution, audit, pinned
configuration and version/diagnostic output are retained in a fresh directory.

A single audit must match the exact request hash and a fresh invocation nonce.
The generated input is regenerated byte-for-byte before execution; arbitrary
or edited Lean programs are not accepted. The configured Lean/mathlib project
and executable are trusted code: this is not a sandbox for malicious Lean
extensions. `lean-toolchain` and `lake-manifest.json` are required and bound;
the reference environment is `.ci/lean-proof`.

A failed bounded proof attempt is `UNKNOWN`, not a mathematical refutation.
Timeout, truncated output, missing tools or an invalid audit cannot authorize a
certificate. Successful proofs are conditional on exactly their declared
premises. Their satisfiability is **not** established by proving the implication.
The closed theorem currently concerns the supported real-expression fragment,
not arbitrary quantified sets, infinite sums or limit theorems.

## SMT: no opaque analytic fallback

`SmtProofBridge` uses `SmtProofArtifacts` and the existing lossless
`SmtLibRenderer`. Goals and all structured assumptions are included. Algebraic
real arithmetic and supported fixed natural powers retain their actual
semantics. Division requires an encoded nonzero or strict-sign premise.
Analytic calls and unsupported symbolic powers are rejected, not encoded as
uninterpreted functions. Use the Lean route for supported real-function proofs;
there is no automatic meaning-changing fallback.

`ProverExecutor.z3()` calls the existing Z3 backend with the exact typed request.
A reported `unsat` alone is insufficient: a second invocation must retrieve a
nonempty proof object. `executeWithEvidence` retains the complete SMT inputs,
stdout/stderr, invocation status and proof object as well as the canonical
native evidence chain. The stored proof text has exactly the certificate hash
reported by the backend. This is a solver proof object, **not** an independent
Lean-kernel replay of Z3's proof.

## Process success is not mathematical evidence

The public `ProverExecutor(command, ...)` constructors are transport-only.
A custom command such as `true` or `cat`, even with a permissive success
predicate, can return only `PROCESS_SUCCEEDED`, never `PROVER_CONFIRMED`.
The raw `cvc5()` factory also remains transport-only until a checked artifact
adapter is supplied. Previous exit-code-only promotion is intentionally removed.

Only the checked `lean(...)` and `z3(...)` factory paths can confirm the exact
request. The worker, demo and web tests explicitly prevent transport success
from being displayed as a mathematical proof. Custom worker injection itself
remains trusted application configuration, not user-supplied proof authority.

## Configuration and reproduction

For Lean configure `REGELSUCHE_LEAN_PROJECT` or `regelsuche.lean.project` to a
pinned, prepared Lean/mathlib project. An installed bare Lean executable is not
enough. `regelsuche.proof.evidence` controls the default evidence root; the
explicit `ProverExecutor.lean(project, evidenceRoot)` and `z3(evidenceRoot)`
factories support application-owned directories.

Generic contract tests do not need a prover installation. Real tool tests are
separate and must actually execute, not merely be skipped:

```sh
export REGELSUCHE_REAL_LEAN=true
export REGELSUCHE_LEAN_PROJECT="$PWD/.ci/lean-proof"
(cd .ci/lean-proof && lake update && lake exe cache get)
mvn -B -pl app -am \
  -Dtest=CheckedLeanRealTest,CheckedProofBridgeRealTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

This run also requires Z3 on PATH. The focused workflow installs the actual
reference tools and retains their evidence. It is distinct from the ordinary
whole-repository CI and the Docker/browser suites. Compiler warnings, skipped
real-tool tests in the ordinary lane, and unrelated test failures must not be
represented as successful complete verification.
