# Polynomial theory subsumption and derived macro cache

## Purpose

Regelsuche can discover or learn a polynomial rewrite that is already an
instance of an exact factorization theory. Such an observation may still be
useful as a search accelerator, but it must not be represented as a new kernel
law or as mathematical novelty.

The authoritative boundary is:

```text
observed left/right expression
  -> ExpressionParser.parseExactTerm
  -> ExactParsedUnivariatePolynomialView over Q[x]
  -> typed FactorizationRequest<ExactRational>
  -> explicitly selected FactorizationEngine<ExactRational>
  -> FactorizationVerifier product reconstruction
  -> ExactFactorizationTransformationPipeline
  -> deterministic rendering and exact reparse
  -> exact representation comparison
  -> theory-subsumption outcome
  -> optional bounded derived-macro cache
```

No coefficient is authorized through `double`, a rounded decimal conversion or
rendered text. The selected engine proposes candidates; only verifier-issued
candidates can reach the transformation and classification boundary.

## Explicit engine selection

`PolynomialTheorySubsumptionClassifier` has no no-argument constructor. Its
caller must provide one `FactorizationEngine<ExactRational>` explicitly.
Consequently, the classifier cannot silently choose a native, external or
best-performing backend after seeing the target result.

The production native integration supplies
`NativeUnivariateFactorizationEngine.boundedRationals()`. Other engines may be
used behind the same verifier contract, but their identity and work remain part
of the retained evidence. The specialized binary-homogeneous quartic operator
is no longer the general theory-classification authority; it remains only a
named historical control.

## Classification contract

The classifier parses both sides with exact literal provenance. The left side
is factored through `ExactParsedFactorizationPipeline`. Every verifier-issued
candidate, up to the classifier's declared finite candidate bound, is then
passed by explicit index through `ExactFactorizationTransformationPipeline`.
That pipeline binds:

- the parser-issued source and literal evidence;
- the exact rational polynomial and typed request;
- the selected engine result;
- independent product reconstruction by `FactorizationVerifier`;
- deterministic rational rendering;
- exact reparse and ring reconstruction;
- source occurrence and transformation work;
- a content-addressed transformation certificate.

The observed right side is compared only with these fully reconstructed
candidate representations. Comparison is exact and deliberately narrower than
general algebraic equivalence:

- exact scalar literals and exact scalar-only arithmetic are normalized;
- addition is compared modulo associativity and commutativity;
- multiplication is compared modulo associativity and commutativity;
- subtraction, division, powers, function calls and argument order remain
  structural and ordered;
- there is no fallback to numerical sampling, a CAS equivalence query or
  expanded-polynomial equality.

This admits harmless factor ordering and grouping differences while preventing
an arbitrary equivalent target from being reported as a representation actually
generated by the configured factorization theory.

## Outcomes

The result has one of five statuses:

- `THEORY_SUBSUMED`: a verifier-issued, exactly reparsed factorization matches
  the observed target representation.
- `NOT_SUBSUMED`: every available exact candidate was examined and none matched,
  or the engine issued no factorization candidate.
- `UNSUPPORTED`: the expression, exact coefficient domain, shape, rendering or
  requested capability lies outside the supported fragment.
- `BUDGET_INCONCLUSIVE`: extraction, engine, verifier, transformation,
  candidate-count or exact-comparison authority was insufficient. This is not a
  negative mathematical conclusion.
- `TECHNICAL_FAILURE`: an engine, evidence or transformation invariant failed.
  This is distinct from an ordinary theory miss.

A positive `Classification` retains:

- `ExactFactorizationTransformationPipeline.TRANSFORMATION_ID` as the theory and
  product-transformation method ID;
- an exact, deterministic source expression normalized without binary
  floating-point conversion;
- the deterministic verifier-derived replacement expression;
- the verifier candidate certificate as the mathematical decomposition
  certificate;
- the full occurrence-bound transformation certificate as the application key;
- the accumulated classifier, factorization, verification, rendering, reparse
  and comparison work;
- `ProjectInventoryNovelty.NOT_EVALUATED`;
- `RetentionDisposition.DERIVED_MACRO_CACHE_ONLY`.

`Classification` has no public constructor. Cache or promotion callers cannot
manufacture positive theory evidence around unrelated patterns or certificates.

## Work and fail-closed behavior

The exact factorization and root-transformation stages retain their existing
non-resettable pipeline work authority. The classifier additionally accounts
for source and target code units, exact structural canonicalization, AC ordering
work and the incremental work of every attempted candidate transformation.

Candidate evaluation is finite. More candidates than the declared classifier
bound result in `BUDGET_INCONCLUSIVE`; candidates are not truncated and then
reported as a definitive miss. An unsupported or budget-inconclusive candidate
also prevents a false `NOT_SUBSUMED` result when it might have been the matching
representation. Source-evidence mismatch and transformation invariant failures
remain technical failures.

## Derived macro cache

`PolynomialDerivedMacroCache` is a deterministic bounded cache outside both the
kernel and the ordinary rule inventory.

A cache entry is keyed by:

- the exact canonical source expression;
- the deterministic generated expression;
- the exact transformation method ID;
- the verifier-issued candidate certificate.

The occurrence-bound transformation certificate is intentionally retained as a
lineage application key rather than as the mathematical macro identity.
Whitespace variants or other source spellings that yield the same canonical
source, verified candidate and generated expression therefore share one cache
slot while preserving their separate source observations.

Each lineage retains:

- application key;
- accumulated work;
- caller-supplied primitive rule IDs;
- source path, generation or other provenance identifiers.

Insertion and FIFO eviction remain deterministic. Cache presence, absence or
eviction has no mathematical meaning.

## Deliberate integration boundary

This classifier migration does not itself:

- install a default engine in the learning module;
- attach an observer to `RuleCandidateMiner`;
- write automatically to `PolynomialDerivedMacroCache`;
- promote any candidate into the kernel or standard inventory;
- authorize cached replay as an executable transition;
- select a production search policy;
- establish performance utility.

The next #748 slice must inject an explicitly configured observer at the merged
`RuleCandidateFormationObserver` boundary, retain positive and negative
classification outcomes separately, and give exactly one owner responsibility
for any bounded cache handoff. Held-out utility and default-policy decisions
remain later frozen experiments.

## Claim boundary

This work establishes only that one explicitly selected exact engine, under its
finite request and work limits, produced a verifier-authorized representation
matching an observed target.

It does not establish external novelty, project-inventory novelty,
independently certified completeness or irreducibility, multivariate
factorization, production authorization, universal CAS superiority or search
speedup.
